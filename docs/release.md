# 版本发布、升级与回滚

## 日常开发流程

1. 从 `main` 新建分支开发，提交后开 PR
2. CI 全部通过才能合并（主分支有保护规则，不能直接推送）。CI 包括：
   - H2 和 MySQL 上的全部测试，**测试覆盖率不能低于下限**（`pom.xml` 里的 `coverage.*.minimum`，只能调高）
   - 部署配置检查；真正启动整套集群做冒烟测试、备份恢复演练和压测
   - CodeQL 代码安全扫描
3. 合并后在 `CHANGELOG.md` 的「未发布」下面记一笔（也可以在 PR 里一起改）

覆盖率报告：本地 `./mvnw test` 后打开 `target/site/jacoco/index.html`；CI 的报告在每次运行的 Artifacts 里。

## 发布一个版本

1. 在 `CHANGELOG.md` 里把「未发布」改成版本号和日期，例如 `## [1.0.0] - 2026-12-01`，上面再加一个空的「未发布」，开 PR 合并
2. 在 `main` 上打标签并推送：
   ```bash
   git switch main && git pull
   git tag v1.0.0
   git push origin v1.0.0
   ```
3. GitHub Actions 的 Release 流程会自动：跑完整测试 → 打包 `shop-1.0.0.jar` → 构建 Docker 镜像推到 `ghcr.io/stormyu324/storm-shop:v1.0.0` → 创建 GitHub Release（发布说明取自 CHANGELOG 对应一节）

版本号：修 bug 升第三位（1.0.1），加功能升第二位（1.1.0），需要手动调整部署的不兼容改动升第一位（2.0.0）。

## 升级（不停业）

先在预发布环境验证（见 [staging.md](staging.md)），然后在正式服务器上：

```bash
git pull                       # 拿到新版本的部署脚本和配置
./deploy/upgrade.sh v1.0.0
```

脚本依次：备份一次 → 拉取镜像 → 先换 `shop-1`、等它健康 → 再换 `shop-2` → 冒烟测试。换一个节点时另一个照常接单，顾客基本无感。任何一步失败都会停下，此时至少有一个节点还在运行旧版本。

镜像默认是私有的，服务器第一次需要登录：在 GitHub 设置里建一个只有 `read:packages` 权限的令牌，然后 `docker login ghcr.io -u 你的GitHub用户名`。

## 回滚

```bash
./deploy/upgrade.sh --rollback   # 回到上一个版本（记录在 .deployed-versions）
./deploy/upgrade.sh v0.9.2       # 或者指定任意旧版本
```

同样是逐个节点替换，不停业。

### 数据库表结构的规则（保证随时能回滚）

表结构由 Flyway 迁移脚本管理（`src/main/resources/db/migration`），只会向前升级、不会自动降级。为了让旧版本代码在新表结构上也能运行（滚动升级时新旧两个版本同时在跑，回滚后旧版本要接着用新表结构），**写迁移脚本必须遵守**：

- **只加不删**：可以加表、加列（必须允许为空或有默认值）、加索引；不要在同一个版本里删列、改列名、改类型
- 确实要删或改：分两个版本做。第一个版本加新列、代码同时写新旧两列；确认不再回滚到更早版本后，第二个版本再删旧列
- 已发布的迁移脚本永远不要修改，有错就写一个新的脚本修正

如果某个版本违反了这些规则、或者升级后发现数据被写坏了，只回滚代码不够，需要连数据一起退回：用 `upgrade.sh` 第 1 步自动生成的备份恢复（`./deploy/restore-cluster.sh backups/storm-升级时间`）。这会丢掉升级之后产生的订单，所以只在万不得已时使用。

## 发布检查清单

- [ ] CHANGELOG 已更新，版本号符合规则
- [ ] 预发布环境：冒烟测试通过、压测没有明显变慢、手动下单 / 付款 / 发货 / 退款走过一遍
- [ ] 新的迁移脚本遵守「只加不删」
- [ ] 正式环境升级后冒烟测试通过，Grafana 面板错误率和响应时间正常
